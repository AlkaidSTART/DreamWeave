# Dreamweave 后端接口边界与安全审查报告

## 1. 审查信息

- 审查日期：2026-07-22
- 审查范围：`app/api/**`、`lib/job-store.ts`、`src/services/**`、上传文件存储、任务状态存储、外部生图服务调用、CI 测试配置和生产依赖
- 审查方式：静态代码审查、生产构建、单元测试、本地接口探测、进程重启验证、`npm audit`
- 当前结论：存在明显的生产安全缺陷和边界处理缺陷，不建议在修复 P0 问题前直接公开部署

## 2. 执行摘要

本次审查确认 2 项 P0、6 项 P1、2 项 P2 问题。

| 等级 | 问题 | 主要影响 |
|------|------|----------|
| P0 | 上传接口可写入并同源托管 HTML | 存储型 XSS、钓鱼页面、用户会话攻击 |
| P0 | 生成、上传、任务接口无认证和限流 | 付费 API 滥用、资源耗尽、任务数据泄露 |
| P1 | 生成请求在 HTTP 生命周期内同步执行 | 请求超时、并发阻塞、服务拒绝服务 |
| P1 | 任务仅保存在进程内存 | 重启丢失、跨实例 404、无法水平扩展 |
| P1 | 图生图和外部 API 参数边界不完整 | provider 行为不一致、超大请求、第三方 URL 抓取风险 |
| P1 | 上传解析和磁盘生命周期无保护 | 内存耗尽、磁盘写满、文件长期暴露 |
| P1 | 外部调用无重试且错误直接返回客户端 | 临时故障放大、内部信息泄露 |
| P1 | 生产依赖存在已知高危漏洞 | 图片处理链可能受已公开漏洞影响 |
| P2 | SSE 缺少连接时限、心跳和异常保护 | 长连接资源泄露、未处理异步异常 |
| P2 | 集成测试命令实际不执行接口测试 | CI 可能在核心接口未验证时错误通过 |

## 3. 已确认问题

### SEC-001：上传接口存在同源存储型 XSS

**等级：P0**

**代码证据**

- `app/api/upload/route.ts:21-25` 只检查客户端可伪造的 `file.type`。
- `app/api/upload/route.ts:35-42` 从用户原始文件名保留扩展名，并将文件直接写入 `public/uploads`。
- 未校验文件 magic number，未根据可信图片格式重新生成扩展名，也未进行图片解码。

**实测证据**

使用 HTML 内容、文件名 `probe.html`、伪造 MIME `image/png` 上传后：

```text
POST /api/upload -> 200
/uploads/<uuid>.html
Content-Type: text/html; charset=UTF-8
```

服务器原样返回并执行同源 HTML 的条件已经成立。审计探针文件已在验证后删除。

**影响**

攻击者可以在应用域名下托管脚本或钓鱼页面。若未来引入 Cookie、登录态或其他同源敏感能力，影响会进一步扩大。

**修复要求**

1. 使用图片解码库校验 magic number 和真实格式，不信任 `file.type`、原始扩展名。
2. 只允许服务端根据解码结果生成固定扩展名，如 `.png`、`.jpg`、`.webp`。
3. 上传文件移出 `public`，通过受控下载接口或对象存储独立域名提供。
4. 响应增加 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`。
5. 增加伪装 HTML、SVG、双扩展名和损坏图片的接口测试。

### SEC-002：后端接口无认证、授权和限流

**等级：P0**

**代码证据**

- `POST /api/generate`、`POST /api/upload`、`POST /api/refine`、`GET /api/jobs/:id` 和 SSE 路由均未校验身份。
- 任务模型不包含 `userId` 或租户归属，查询接口没有对象级授权。
- 项目没有 middleware、API key 校验或限流实现。

**实测证据**

- 未携带任何凭据即可创建和查询任务。
- 连续请求 12 次 `POST /api/refine`，12 次均返回 `200`。
- 任意知道任务 ID 的客户端可读取原始提示词、润色提示词和生成结果。

**影响**

- 公开部署后，任何人都能消耗 `IMAGE_GENERATION_API_KEY` 对应的付费额度。
- 可通过生成请求、上传和 SSE 长连接耗尽 CPU、内存、连接数及磁盘。
- 任务 ID 泄露后会造成用户提示词和图片结果越权访问。

**修复要求**

1. 生产环境至少增加服务端 API key；面向多用户时使用正式身份认证。
2. 任务必须绑定 `userId`，所有查询和 SSE 接口执行对象级授权。
3. 对生成接口实施 IP + 用户双维度限流，至少满足每分钟 10 次上限。
4. 增加并发任务数、每日额度和单用户未完成任务数限制。
5. CORS 使用明确 Origin 白名单，禁止动态反射任意 Origin。

### BND-001：生成接口同步执行全部外部调用

**等级：P1**

**代码证据**

- `app/api/generate/route.ts:32` 等待 `createJob()` 完成后才响应。
- `lib/job-store.ts:48-78` 在请求内完成提示词处理和全部图片生成。
- `src/services/AgnesProvider.ts:103` 单次调用超时为 120 秒。
- 图片数量最多为 4，最坏请求可占用约 480 秒，且尚未计入网络和存储开销。

**实测证据**

使用无外部费用的 fallback provider 请求 4 张图片，返回体中的任务已经是 `completed`、进度 `100`，证明接口不是“创建任务后立即返回”。

**影响**

- 与 `/api/jobs/:id` 和 SSE 的异步任务设计冲突。
- 容易超过反向代理、Serverless Function 和客户端超时。
- 少量慢请求即可长期占用服务并发。
- 生成中途失败时客户端拿不到已创建的任务 ID，只得到 `500`。

**修复要求**

恢复队列/Worker 边界：接口完成验证和持久化后返回 `202 + jobId`，外部生图只允许在 Worker 中执行；配置并发、超时、取消、重试和幂等。

### BND-002：任务状态仅保存在单进程内存

**等级：P1**

**代码证据**

- `src/services/JobStorageService.ts:4` 使用进程内 `Map`。
- 全局 `jobStorage` 单例没有 TTL、容量上限或持久化。

**实测证据**

创建任务后 `GET /api/jobs/:id` 返回 `200`；重启同一生产服务后，相同任务 ID 返回 `404`。

**影响**

- 部署、崩溃或扩缩容后任务全部丢失。
- 多实例环境中，创建和查询落到不同实例会随机 `404`。
- Map 无上限增长，可导致内存耗尽。

**修复要求**

使用 Redis/BullMQ 或持久化数据库保存任务状态；增加 TTL、最大历史数量、失败清理和多实例一致性测试。

### BND-003：图生图和外部服务参数验证不完整

**等级：P1**

**代码证据**

- `app/api/generate/route.ts:11-15` 允许任意长度、任意内容的 `inputImage`、`model`、`size` 和 `ratio`。
- Schema 没有要求 `type=image-to-image` 时必须提供合法 `inputImage`。
- `src/services/AgnesProvider.ts:62-83` 将用户参数和图片 URL/Data URL直接转发给第三方。
- `model`、`size`、`ratio` 没有白名单，`ratio` 当前接收后未使用。

**实测证据**

- Agnes provider 下缺少 `inputImage` 返回 `500`，错误为“图生图模式必须提供 inputImage”，本应在路由层返回 `400`。
- fallback provider 下相同无效请求返回 `200 completed`，说明接口语义依赖 provider。

**影响**

- 可通过超大 Data URL 绕过提示词长度边界并占用大量内存。
- 任意外部 URL 被交给第三方抓取，可能触发第三方 SSRF、内网探测或流量滥用。
- 任意模型和尺寸可能造成费用不可控或第三方接口异常。

**修复要求**

使用 Zod 判别联合；图生图必须引用本系统已验证的上传 ID。限制 Data URL 大小和格式，禁止任意 URL；模型、尺寸、比例使用服务端白名单，客户端只传受控枚举。

### SEC-003：上传请求和文件生命周期可导致资源耗尽

**等级：P1**

**代码证据**

- `app/api/upload/route.ts:11` 在检查 `file.size` 前调用 `request.formData()`，请求体已经被解析进内存。
- 文件直接写入应用本地磁盘，没有用户额度、总容量、文件数量或磁盘水位限制。
- 没有实现约束文档要求的 24 小时或 7 天定时清理。

**影响**

攻击者可并发发送大 multipart 请求造成内存压力，或持续上传小于 10 MB 的文件写满磁盘。Serverless 环境中本地文件也不具备持久性和跨实例一致性。

**修复要求**

在网关层限制请求体；上传改为流式处理；实施用户/IP 配额、并发限制、对象存储和生命周期策略；上传失败时清理临时文件。

### ERR-001：外部 API 无重试，内部错误直接暴露

**等级：P1**

**代码证据**

- `src/services/AgnesProvider.ts:95-152` 只有单次 fetch 和超时，没有约束要求的指数退避重试。
- `src/services/AgnesProvider.ts:107-110` 将第三方完整错误响应拼接到异常。
- `app/api/generate/route.ts:40-44` 和上传路由直接把异常消息返回客户端。

**影响**

临时网络抖动直接导致任务失败；第三方响应、文件系统路径、网络错误和内部实现信息可能暴露给客户端。

**修复要求**

只对可重试状态码执行有限指数退避；对客户端返回稳定错误码和通用信息；详细错误写入经过脱敏的服务端日志并附带 request ID。

### DEP-001：生产依赖存在已知漏洞

**等级：P1**

2026-07-22 执行：

```bash
npm audit --omit=dev --audit-level=moderate
```

结果为 3 个漏洞：1 个 moderate、2 个 high。

- `next@16.2.10` 内嵌 `postcss@8.4.31`，命中 PostCSS 输出转义问题。
- `sharp@0.34.5` 命中 libvips 继承漏洞，审计报告列出 CVE-2026-33327、CVE-2026-33328、CVE-2026-35590、CVE-2026-35591。

不要直接执行报告建议的 `npm audit fix --force`，该建议会产生不合理的 Next.js 大版本回退。应先确认 Next.js 官方修复版本，再进行受控升级并重新构建、测试图片处理路径。

### REL-001：SSE 连接缺少完整生命周期保护

**等级：P2**

**代码证据**

- `app/api/jobs/[jobId]/stream/route.ts:26-63` 使用 500 ms 轮询，没有最大连接时长和心跳。
- interval 回调是异步函数，没有 try/catch；存储异常会形成未处理 rejection。
- abort 和 interval 完成路径都可能关闭 controller，缺少幂等关闭保护。

**影响**

大量空闲连接会持续消耗连接和定时器资源；代理可能因无心跳中断；异常路径可能产生运行时错误。

**修复要求**

增加认证、每用户连接上限、15-30 秒心跳、最大时长、幂等清理和异常捕获。任务事件应由队列/Redis PubSub 推送，避免高频轮询。

### TST-001：集成测试命令没有执行接口测试

**等级：P2**

**实测证据**

```text
npm run test:integration
Test Files 9 skipped
Tests 41 skipped
```

`package.json` 通过测试名称包含 `integration` 来筛选，但仓库没有对应测试。CI 中该命令退出码为 0，因此接口完全未验证也会显示通过。

**缺失覆盖**

- `app/api/generate/route.ts`
- `app/api/upload/route.ts`
- `app/api/jobs/[jobId]/route.ts`
- `app/api/jobs/[jobId]/stream/route.ts`
- 认证、授权、限流、文件 magic number、请求体上限和错误脱敏

**修复要求**

建立 `tests/integration/**/*.test.ts`，让脚本按目录执行；当没有匹配测试时必须失败。CI 增加依赖审计或 SCA、上传恶意样本测试和关键 API 合约测试。

## 4. 已有有效防护

- 提示词长度限制为 1-2000 字符。
- 单次图片数量限制为 1-4 张。
- 上传文件名主体使用 `crypto.randomUUID()`，降低直接路径遍历风险。
- Agnes 外部调用配置了 120 秒超时。
- Lint、TypeScript、生产构建和现有 41 个单元测试通过。

这些措施不能抵消前述 P0/P1 问题。

## 5. 建议修复顺序

### 第一阶段：阻断公开攻击面

1. 修复上传同源 XSS，停止直接写入 `public`。
2. 为所有非公开接口增加认证、对象级授权和限流。
3. 关闭任意模型、尺寸、URL 和 Data URL 输入。
4. 升级受影响依赖并验证官方修复版本。

### 第二阶段：恢复可靠任务边界

1. 将生成流程迁移到持久化队列和独立 Worker。
2. 使用 Redis/数据库保存任务，增加 TTL、配额、幂等和取消能力。
3. 将生成接口改为 `202 Accepted`，立即返回 `jobId`。
4. 统一所有 provider 的输入校验和错误语义。

### 第三阶段：补齐纵深防护

1. 实现上传流式处理、对象存储和生命周期清理。
2. 实现外部调用重试、熔断、错误脱敏和可观测性。
3. 完善 SSE 生命周期和连接配额。
4. 添加真实接口集成测试、安全回归测试和 CI 失败门禁。

## 7. 发布门禁结论

当前状态不满足 `harness/rules/architecture/16-安全架构约束.md`、`harness/rules/project/05-安全约束.md`、`harness/rules/architecture/19-容错架构约束.md` 和 `harness/rules/architecture/21-性能架构约束.md`。

在 SEC-001、SEC-002、BND-001 和 DEP-001 修复并完成接口安全回归测试前，不建议合并到生产分支或公开部署。
