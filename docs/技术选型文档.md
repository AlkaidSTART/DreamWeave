## 2. 前端技术选型

### 2.1 Next.js 16

**选型理由**:
- **App Router**: 支持服务端组件、布局、流式传输和数据获取的现代化路由方案
- **Server Components**: 默认使用服务端组件，减少客户端JavaScript包体积，提升性能
- **Route Handlers**: 内置API路由，无需额外配置即可创建RESTful接口
- **自动优化**: 自动处理图片优化、字体优化、脚本优化
- **React 19兼容**: 完整支持React 19并发特性

**关键特性**:
- Server Components与Client Components的混合使用
- 基于文件系统的路由结构
- 自动生成静态和动态路由
- 内置SSE支持（用于实时进度推送）

**边界考虑**:
- Server Components不支持客户端状态管理（useState/useEffect）
- SSE连接在Next.js Edge Runtime中有连接时长限制
- 服务端组件的异步数据获取需要注意错误处理

### 2.2 React 19

**选型理由**:
- **并发特性**: 支持并发渲染、Suspense、Transition
- **Hooks完善**: useState、useEffect、useContext、useReducer等标准Hooks
- **服务器组件**: 原生支持服务端组件模式
- **生态成熟**: 丰富的第三方库和工具支持

**关键特性**:
- 并发模式下的异步数据获取
- Suspense边界处理
- Server Actions（可选，用于表单提交）

**边界考虑**:
- React 19与Jest存在兼容性问题，建议使用Vitest
- 并发模式下的状态更新需要注意可预测性

### 2.3 Tailwind CSS 4

**选型理由**:
- **CSS-first配置**: 无需tailwind.config.js，使用CSS变量定义主题
- **@theme指令**: 在CSS中直接定义设计令牌、断点、颜色等
- **零运行时**: 编译时生成CSS，无客户端运行时开销
- **灵活性**: 支持自定义工具类、变体、层叠

**关键特性**:
```css
@import "tailwindcss";

@theme {
  --color-primary: #8B5CF6;
  --color-primary-dark: #7C3AED;
  --font-sans: 'Geist', sans-serif;
  --breakpoint-xl: 1280px;
}
```

**边界考虑**:
- 需要完整的CSS扫描配置，确保所有文件被正确处理
- 主题变量命名需要遵循规范，避免冲突

## 3. 后端技术选型

### 3.1 Node.js

**选型理由**:
- **全栈JavaScript**: 前后端统一语言，降低开发成本
- **异步非阻塞**: 适合IO密集型任务（图片生成、API调用）
- **生态丰富**: npm包管理，丰富的第三方库支持
- **性能优化**: V8引擎持续优化，支持Worker Threads

**版本要求**: Node.js 20.x+

**边界考虑**:
- 单线程模型需要注意CPU密集型任务的处理
- 内存管理需要关注大图片处理场景

### 3.2 BullMQ

**选型理由**:
- **基于Redis**: 可靠的消息队列，支持持久化
- **并发控制**: 支持Worker并发数配置
- **重试机制**: 内置重试策略（fixed、exponential）
- **任务管理**: 支持任务优先级、延迟、依赖关系

**关键配置**:
```typescript
import { Worker } from 'bullmq';

const worker = new Worker('image-generation', processor, {
  connection: {
    host: process.env.REDIS_HOST,
    port: parseInt(process.env.REDIS_PORT),
  },
  concurrency: 4,
  attempts: 3,
  backoff: {
    type: 'exponential',
    delay: 1000,
  },
});
```

**边界考虑**:
- Redis可用性直接影响队列系统稳定性
- 长时间运行的Worker需要进程监控和自动重启
- 任务失败处理需要明确的告警机制

### 3.3 ioredis

**选型理由**:
- **高性能**: 优于node-redis的性能表现
- **Cluster支持**: 原生支持Redis Cluster模式
- **连接池**: 内置连接池管理，复用连接
- **连接管理**: 自动重连、连接状态监控

**关键配置**:
```typescript
import Redis from 'ioredis';

const redis = new Redis({
  host: process.env.REDIS_HOST,
  port: parseInt(process.env.REDIS_PORT),
  password: process.env.REDIS_PASSWORD,
  retryDelayOnFailover: 200,
  enableReadyCheck: true,
  lazyConnect: false,
});
```

**边界考虑**:
- 连接参数需要根据生产环境调整
- Cluster模式需要额外配置节点发现
- 连接失败重试策略需要合理设置

### 3.4 Sharp

**选型理由**:
- **高性能**: 基于libvips，性能远超其他图片处理库
- **格式转换**: 支持JPEG、PNG、WebP、AVIF、GIF等格式
- **流式处理**: 支持流式输入输出，减少内存占用
- **丰富API**: 支持resize、crop、rotate、composite等操作

**关键配置**:
```typescript
import sharp from 'sharp';

await sharp(inputBuffer)
  .resize(1024, 1024, { fit: 'cover' })
  .toFormat('png')
  .toFile(outputPath);
```

**边界考虑**:
- 需要安装libvips依赖（系统级）
- 大图片处理需要注意内存使用
- 格式转换可能导致质量损失

## 4. 测试技术选型

### 4.1 Vitest

**选型理由**:
- **Jest兼容**: API与Jest高度兼容，迁移成本低
- **ESM支持**: 原生支持ES模块，无需额外配置
- **更快的速度**: 基于esbuild，启动和运行速度更快
- **React 19兼容**: 更好地支持React 19的并发特性

**边界考虑**:
- 部分Jest特性可能不完全支持
- 社区生态相对Jest较小

### 4.2 Playwright

**选型理由**:
- **跨浏览器**: 支持Chrome、Firefox、Safari
- **自动等待**: 智能等待元素出现，减少不稳定测试
- **网络拦截**: 支持mock网络请求
- **移动端模拟**: 支持移动设备测试

## 5. 架构边界分析

### 5.1 数据持久化边界

**问题**: PRD中未定义独立数据库层，所有状态依赖Redis/BullMQ

**风险**:
- Redis数据结构有限，复杂查询困难
- Redis内存限制，历史记录存储受限
- 数据备份和恢复需要额外方案

**应对策略**:
- 使用Redis Hash存储Job元数据
- 使用Redis List存储历史记录（限制长度）
- 考虑定期将历史数据归档到对象存储
- 重要配置数据使用环境变量或配置文件

### 5.2 文件存储边界

**问题**: PRD中使用本地文件存储（`public/uploads/`）

**风险**:
- 本地存储不支持水平扩展
- 文件丢失风险（服务器故障）
- 存储容量受限

**应对策略**:
- 开发环境使用本地存储
- 生产环境考虑云对象存储（S3、OSS）
- 实现存储抽象层，支持多种存储后端切换
- 文件生命周期管理（定期清理过期文件）

### 5.3 Worker进程管理边界

**问题**: PRD中定义独立Worker进程（`worker.js`）

**风险**:
- Worker进程需要独立部署和监控
- 进程崩溃可能导致任务丢失
- 资源分配需要合理配置

**应对策略**:
- 使用PM2或Docker进行进程管理
- 配置进程自动重启和健康检查
- 使用BullMQ的任务重试机制
- 监控Worker状态和任务队列长度

### 5.4 SSE实现边界

**问题**: Next.js App Router中SSE的实现约束

**风险**:
- Edge Runtime有连接时长限制
- SSE连接可能被反向代理中断
- 高并发下的资源消耗

**应对策略**:
- 使用Node.js Runtime而非Edge Runtime
- 配置反向代理的超时时间
- 实现连接心跳机制
- 考虑使用WebSocket作为备选方案

## 8. 文档同步说明

### 8.1 需要同步更新的文档

| 文档 | 需要更新的内容 | 优先级 |
|------|----------------|--------|
| PRD文档 | `package.json` scripts中的测试命令从Jest改为Vitest | 高 |
| TDD文档 | Jest配置示例改为Vitest配置示例 | 高 |
| TDD文档 | 测试命令从`npm run test:unit`等改为Vitest命令 | 高 |

### 8.2 测试框架变更说明

**变更原因**: React 19与Jest存在兼容性问题，Vitest提供更好的React 19支持和更快的运行速度。

**变更内容**:
- 将`jest`替换为`vitest`
- 将`ts-jest`替换为`@vitest/tsconfig`
- 将`jest.config.js`替换为`vitest.config.ts`
- 测试命令保持兼容（`npm test`, `npm run test:unit`等）
