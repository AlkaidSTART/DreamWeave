## 🔴 高优先级问题 (P0)

### 1. TypeScript 配置不符合规范要求

**位置**: `tsconfig.json`

**问题描述**:
根据 `harness/rules/coding/01-typescript规范.md` 的要求，项目应启用以下严格模式选项：

```json
{
  "compilerOptions": {
    "noImplicitAny": true,
    "noImplicitReturns": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "exactOptionalPropertyTypes": true,
    "strictNullChecks": true,
    "strictFunctionTypes": true,
    "strictPropertyInitialization": true,
    "useUnknownInCatchVariables": true
  }
}
```

**当前状态**:
项目仅启用了 `"strict": true`，但缺少显式的细粒度配置。虽然 `strict: true` 包含了部分选项，但规范要求显式声明所有约束以确保团队对配置的明确理解。

**影响**:
- 可能存在隐式 `any` 类型未被捕获
- 未使用的变量和参数未被检测
- 类型安全性不足

**修复建议**:
更新 `tsconfig.json`，显式添加所有必需的严格模式选项。

### 2. 环境变量暴露风险

**位置**: `.env`, `.env.local`

**问题描述**:
项目中存在多个环境变量文件（`.env`, `.env.local`, `.env.example`），且 `.gitignore` 虽然包含了 `.env*` 但仍存在以下问题：

1. `.env` 文件存在于版本控制中（根据 `ls -la` 输出）
2. 根据 `harness/rules/project/05-安全约束.md`，所有包含敏感信息的环境变量文件应被完全排除在版本控制之外
3. 多个环境文件可能导致配置混淆

**影响**:
- API 密钥、数据库连接字符串等敏感信息可能泄露
- 违反安全架构约束

**修复建议**:
```bash
# 1. 从版本控制中移除 .env 和 .env.local
git rm --cached .env .env.local

# 2. 确保 .gitignore 正确配置
echo ".env*" >> .gitignore
echo "!.env.example" >> .gitignore

# 3. 只保留 .env.example 作为模板
```

### 3. API 路由缺少统一的错误处理和日志记录

**位置**: `app/api/*/route.ts`

**问题描述**:
根据 `harness/rules/project/07-错误处理约束.md`，所有错误必须记录到日志，但当前实现存在以下问题：

1. **空 catch 块**: 多个 API 路由使用空的 `catch` 语句
   ```typescript
   // app/api/auth/logout/route.ts
   } catch {
     return NextResponse.json(
       { success: false, error: "退出失败" },
       { status: 500 },
     );
   }
   ```

2. **缺少日志记录**: 错误未被记录，无法追踪生产环境问题

3. **错误信息泄露**: 某些路由直接返回错误消息，可能泄露内部实现细节
   ```typescript
   // app/api/refine/route.ts
   const message = error instanceof Error ? error.message : "润色失败";
   ```

**影响**:
- 生产环境问题难以追踪和调试
- 违反错误处理约束
- 可能泄露敏感信息

**修复建议**:
1. 创建统一的错误处理中间件或工具函数
2. 所有 catch 块中添加错误日志记录
3. 区分开发环境和生产环境的错误消息

```typescript
// lib/error-handler.ts
export function logError(error: unknown, context: string) {
  console.error(`[${context}]`, error instanceof Error ? error.stack : error);
}

export function formatErrorResponse(error: unknown, isDevelopment: boolean) {
  if (isDevelopment && error instanceof Error) {
    return error.message;
  }
  return "服务器内部错误";
}
```

### 4. 缺少输入验证的安全防护

**位置**: `app/api/upload/route.ts`, `app/api/generate/route.ts`

**问题描述**:
1. **文件上传**: 虽然有文件类型和大小验证，但缺少以下安全检查：
   - 文件内容验证（MIME 类型欺骗）
   - 文件名安全处理（路径遍历攻击）
   - 上传频率限制

2. **提示词注入**: `app/api/generate/route.ts` 和 `app/api/refine/route.ts` 接受用户输入的提示词，但未进行内容安全检查

**影响**:
- 可能被用于上传恶意文件
- 提示词注入攻击
- DoS 攻击风险

**修复建议**:
1. 添加文件内容验证（魔数检查）
2. 对上传的文件名进行安全清理
3. 实现速率限制中间件
4. 对提示词进行内容审核（长度、敏感词过滤）

## 🟡 中优先级问题 (P1)

### 5. 架构约束违反：API 层包含业务逻辑

**位置**: `lib/job-store.ts`

**问题描述**:
根据 `harness/rules/architecture/11-系统架构约束.md`：
> "API层禁止直接调用外部服务，必须通过队列层"

但 `lib/job-store.ts` 中的 `createJob` 函数直接在 API 层被调用，且包含业务逻辑：

```typescript
// lib/job-store.ts
export async function createJob(
  request: CreateGenerationRequest,
  userId: string,
): Promise<GenerationJob> {
  // ... 业务逻辑
  await jobStorage.save(job, userId);
  await addImageGenerationJob(id, userId, request);
  return job;
}
```

这违反了分层架构原则，应该将业务逻辑移到服务层。

**影响**:
- 架构混乱，职责不清
- 难以维护和测试
- 违反系统架构约束

**修复建议**:
将 `lib/job-store.ts` 重构为服务层：
```
src/services/JobService.ts
```
并确保 API 层只负责请求路由和参数验证。

### 6. 缺少 API 响应格式的统一实现

**位置**: 所有 `app/api/*/route.ts`

**问题描述**:
虽然 `lib/types.ts` 定义了统一的 `ApiResponse<T>` 接口：

```typescript
export interface ApiResponse<T = unknown> {
  success: boolean;
  data?: T;
  message?: string;
  error?: string;
}
```

但实际使用中不一致：
1. 有些路由返回 `{ success, data }`
2. 有些路由返回 `{ success, error }`
3. 有些路由返回 `{ success, message }`
4. 缺少统一的响应构造函数

**影响**:
- 前端需要处理多种响应格式
- 违反 API 规范约束
- 增加维护成本

**修复建议**:
创建统一的响应构造函数：

```typescript
// lib/api-response.ts
export class ApiResponseBuilder {
  static success<T>(data: T, message?: string): ApiResponse<T> {
    return { success: true, data, message };
  }

  static error(error: string, statusCode: number = 500): ApiResponse {
    return { success: false, error };
  }
}
```

### 7. Redis 连接未实现重试和健康检查

**位置**: `lib/redis.ts` (未在代码中看到，但在 `src/queue/imageQueue.ts` 中被引用)

**问题描述**:
根据 `harness/rules/project/07-错误处理约束.md`：
> "Redis连接失败: 无限重试，指数退避"

但当前实现中未看到 Redis 连接的错误处理和重试逻辑。

**影响**:
- Redis 连接失败时应用可能崩溃
- 缺少容错机制
- 违反错误处理约束

**修复建议**:
```typescript
// lib/redis.ts
import Redis from 'ioredis';

export const redis = new Redis(process.env.REDIS_URL!, {
  retryStrategy: (times) => {
    const delay = Math.min(times * 50, 2000);
    return delay;
  },
  maxRetriesPerRequest: 3,
  enableReadyCheck: true,
  lazyConnect: false,
});

redis.on('error', (err) => {
  console.error('[Redis] Connection error:', err);
});

redis.on('connect', () => {
  console.log('[Redis] Connected');
});
```

建议按照推荐的修复顺序逐步改进，优先处理安全和配置问题，然后进行架构重构和功能完善。
